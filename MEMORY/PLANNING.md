> Scope: turning goals into briefs, specs, roadmaps and task lists · Pairs with: [[MEMORY/THINKING|THINKING]], [[MEMORY/PROJECTS|PROJECTS]], [[MEMORY/BUSINESS|BUSINESS]] (product specs), [[MEMORY/CODING|CODING]] (software plans follow SDSI)

## Core Rules (non-negotiable)

### RULE#1 Outcome before solution
Pin down the goal, audience, constraints and success criteria before proposing steps.

### RULE#2 Measurable done
Success criteria are verifiable outcomes, not activities. Words like "gracefully", "user-friendly" and "works properly" don't count.

### RULE#3 Plan size matches task size
A one-sentence change needs no plan. Unsure of the size? Take the heavier path; upgrade when complexity appears, never downgrade.

### RULE#4 Only decision-changing questions
Ask at most 5 (fewer is better), numbered, each with your recommended answer, so "yes" accepts them all. Fill low-stakes gaps with defaults and list them as assumptions.

### RULE#5 Gate the big stuff
Large or irreversible work: get sign-off on the plan first. Don't present a plan and start executing it in the same message.

## Defaults
- State scope and non-goals; cut anything no goal needs.
- Split work into independently deliverable chunks, each ending in a checkable result.
- Pre-mortem: top 3 risks, each tied to a mitigation, a gate or an owner.
- No placeholders ("TBD", "handle edge cases", "as appropriate"); every step decides something.
- Every project has a next action; every action has an owner and a date.
- Pair each success metric with a counter-metric.
- Self-review before handing over: coverage, contradictions, ambiguity, proportion.
- Task lists: Active / Waiting on / Someday / Done; tag "for [person]", "due [date]".
- Software work follows SDSI's INTENT → SPEC → PLAN chain ([[MEMORY/CODING|CODING]]).

## Avoid
- Asking for facts you can look up.
- Template theatre: boilerplate personas, vision statements that drive no decision, sections marked N/A.
- A plan longer than the work.

## Output
```text
Goal: one sentence
Approach: 1–2 sentences
Constraints / Non-goals
- [ ] Step · deliverable · how it's verified
Risks → mitigation
Open questions (5 max), each with "Recommended: X"
```
